# AGENTS.md

## 적용 범위

이 파일의 규칙은 `lib/` 디렉터리 이하의 Flutter/Dart 코드 작업에 적용된다.

이 디렉터리에서 Codex는 프로젝트 루트 AGENTS.md의 규칙을 따르되,
특히 Flutter 코드 작성 및 수정 시 아래 규칙을 우선 고려한다.


---

# 핵심 원칙

## 1. 승인 없는 수정 금지

Codex는 사용자 승인 없이 `lib/` 아래의 파일을 수정하지 않는다.

반드시 다음 순서를 따른다.

1. 작업 목표 설명
2. 수정할 파일 목록 제시
3. 수정 이유 설명
4. 사용자 승인 요청
5. 승인 후 코드 수정 제안

자동 수정 전제 금지.


---

## 2. 파일 확인 없는 추측 금지

Flutter 코드 변경 전에는 반드시 현재 파일 상태를 확인한다.

특히 다음 항목은 추측하지 않는다.

- 위젯이 StatelessWidget인지 StatefulWidget인지
- 생성자 파라미터 이름
- import 경로
- 모델 필드 이름
- Map 키 이름
- Repository 메서드 이름
- BuildContext 사용 위치

필요한 파일이 없으면 먼저 요청한다.


---

## 3. 수정 위치는 정확하게

수정 제안 시 반드시 포함한다.

- 파일 경로
- 클래스 이름
- 메서드 이름
- 삽입 / 교체 / 삭제 여부
- 앞뒤 문맥 코드

"이 부분을 고친다" 같은 모호한 표현은 피한다.


---

# Flutter 구조 규칙

## 4. 현재 프로젝트 구조

이 프로젝트는 다음 구조를 사용한다.

- `lib/main.dart` : 앱 시작점
- `lib/database/` : DB 연결 관리
- `lib/data/models/` : 데이터 모델
- `lib/data/repositories/` : DB 조회 로직
- `lib/ui/` : 화면 UI

Codex는 이 구조를 존중한다.
대규모 구조 변경은 사용자의 명시적 승인 없이는 하지 않는다.


---

## 5. UI와 DB 직접 결합 금지

UI 파일(`lib/ui/`)에서 SQL을 직접 작성하지 않는다.

데이터 접근은 다음 순서로 한다.

UI
→ Repository
→ DatabaseService

즉, UI는 Repository를 통해서만 DB 데이터를 요청한다.


---

## 6. 모델 우선

가능하면 `Map<String, dynamic>` 직접 사용을 줄이고
모델 클래스를 사용한다.

예:

- `Word`
- `WordRelation`

단, 기존 흐름을 깨뜨리지 않기 위해
점진적으로 모델로 전환할 수 있다.


---

## 7. StatefulWidget 사용 기준

다음 경우에는 StatefulWidget 사용을 고려한다.

- 비동기 로딩 필요
- initState 필요
- 노드 클릭 등 상태 변화 발생
- 그래프 재렌더링 필요

반대로 단순 정적 출력 화면은 StatelessWidget 유지 가능.


---

# 그래프 화면 규칙

## 8. 그래프 구현 우선순위

그래프 기능은 다음 순서로 구현한다.

1. 중심 노드
2. 더미 노드
3. 원형 자동 배치
4. 연결선 동기화
5. 실제 DB 연결
6. 노드 클릭 탐색
7. 관계 타입 시각화
8. Split View 확장

한 번에 고난도 기능을 몰아서 추가하지 않는다.


---

## 9. 그래프 데이터 소스

그래프의 실제 관계 데이터는 반드시 `WORD_RELATION`을 기반으로 한다.

`WORD_TABLE`의 `관련1~7` 컬럼은
그래프의 주 데이터 소스로 사용하지 않는다.

그래프 연결 흐름은 다음을 따른다.

- 중심 단어 선택
- `WORD_RELATION` 조회
- 연결 단어 ID 수집
- `WORD_TABLE`에서 연결 단어 조회
- 노드 렌더링


---

## 10. 그래프 상태 관리

그래프에서 가장 중요한 상태는 "현재 중심 단어"이다.

즉, 항상 다음 질문에 답할 수 있어야 한다.

- 현재 중심 단어는 무엇인가?
- 현재 연결 단어 목록은 무엇인가?

이 상태가 명확하지 않으면 구조 변경을 제안하지 않는다.

# UI 작성 규칙

## 11. 한글 주석 필수

새 파일을 만들 때는 파일 상단에 한글 설명 주석을 추가한다.

새 클래스/핵심 메서드에도 한글 주석을 추가한다.

주석은 다음을 설명해야 한다.

- 이 파일/클래스의 역할
- 왜 이런 구조를 쓰는지
- 향후 확장 방향이 무엇인지


---

## 12. 가독성 우선

복잡한 위젯 트리를 만들 때는 다음을 우선한다.

- 메서드 분리
- 의미 있는 함수명 사용
- 중첩 최소화

예:

- `_buildCenterNode()`
- `_buildWordNodes()`
- `_buildRelationNode()`

이름이 역할을 설명해야 한다.


---

## 13. const 사용 규칙

`const`는 가능한 경우만 사용한다.

다음 경우에는 const를 강제하지 않는다.

- non-const 필드 사용
- runtime 값 사용
- 상태 객체 사용
- Theme.of(context) 의존
- FutureBuilder / LayoutBuilder / CustomPainter 조합

즉, const 에러를 피하기 위해
"필요할 때만 const" 원칙을 따른다.


---

# Repository 규칙

## 14. Repository는 DB 구조에 맞게 작성

Repository 메서드 이름은 실제 구현과 일치해야 한다.

존재하지 않는 메서드명을 가정하지 않는다.

예:
- `getConnectedWords(String wordId)` 가 실제 존재하면 그 이름을 그대로 사용
- `getRelations()` 같은 가상의 이름을 만들지 않는다


---

## 15. DatabaseService 구조 존중

DatabaseService 접근 방식은 실제 구현을 따른다.

예:
- `DatabaseService.openDatabaseFile()`
- 또는 singleton 구조

실제 파일을 확인하지 않고 `instance` 같은 접근 방식을 추측하지 않는다.


---

# 디버깅 규칙

## 16. 오류 원인 설명 순서

에러를 설명할 때는 다음 순서를 따른다.

1. 무엇이 문제인지
2. 왜 그런지
3. 어떻게 고치는지
4. 어디를 수정해야 하는지

사용자는 비전문가일 수 있으므로
원인과 해결을 분리해서 설명한다.


---

## 17. print 디버깅은 임시로만

디버깅을 위해 `print()`를 넣을 수 있다.
하지만 확인 후에는 제거를 제안한다.

디버그 출력은 영구 코드로 남기지 않는다.

# Git 규칙

## 18. 커밋 타이밍 제안

Codex는 다음 상황에서 커밋을 제안한다.

- 기능 하나가 실행까지 확인된 경우
- 구조 리팩토링이 안정화된 경우
- 그래프 UI 단계가 하나 끝난 경우

커밋 메시지는 항상 한국어로 제안한다.


---

## 19. 브랜치 제안

다음과 같은 경우 새 브랜치를 제안한다.

- 기능이 크게 갈라질 때
- 그래프 UI → 데이터 연결처럼 단계가 바뀔 때
- 탐색 기능처럼 별도 실험이 필요한 경우

예:
- `feature/word-graph-v1`
- `feature/word-graph-data-binding`
- `feature/word-graph-navigation`


---

# 현재 프로젝트에서 중요한 사실

## 20. 현재 Flutter 코드에서 특히 주의할 점

- `WordGraphScreen`은 그래프 핵심 화면이다.
- 중심 단어와 연결 단어 상태를 분리해서 생각한다.
- 그래프는 장기적으로 Split View 확장을 고려하지만,
  지금은 작은 단계로 안정적으로 구현한다.
- Word 모델 필드명과 DB 컬럼명 매핑을 혼동하지 않는다.
- 실제 데이터와 더미 데이터를 섞을 때는 현재 단계가 무엇인지 명확히 한다.
